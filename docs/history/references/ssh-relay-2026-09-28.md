## Findings

1. The sandssh Python relay accepts a `SANDSSH1` node or client
   announcement and pairs one waiting node socket with one client
   (`references/talaria0101__sandssh/tree/relay/sandssh-relay.py:78-128`,
   commit `4fc7f8c`). Its README says the concurrent reverse path lives
   in dropssh, and that the simple relay stays one session per connection
   (`references/talaria0101__sandssh/tree/README.md:29-45`, same commit).
2. The current dropssh `serve.c` defines a session row and a table, sends
   node data with an id, and starts one reader for the node websocket
   (`references/talaria0101__dropssh/tree/src/serve.c:313-338`,
   `:574-581`, `:1016-1032`, commit `0aafa21`).
   `tests/mux-probe.py` checks that a node frame without an id closes
   with code 1009. This is a different route from the Python relay.
3. The dropssh README at the captured commit still says `serve` handles
   one session (`references/talaria0101__dropssh/tree/README.md:120-126`).
   Its `serve.c` and relay issue record show the concurrent
   implementation. The code and test settle the current behaviour; the
   README sentence is stale. Sandssh issue 12 also describes dropssh
   before that implementation; it is a dated request, not a current
   source result.
4. PR 67 accepts `SANDSSH1` as a protocol alias, uses a socketpair for a
   server, and exercises a real SSH client in its own test. Its proposed
   T-1401 closes on twelve cases against the simple relay. Those cases do
   not prove the dropssh concurrent route. Its proposed T-1402 says
   sandssh contains `errandsh`; the captured sandssh README instead
   names a separate sandhome tree
   (`references/talaria0101__sandssh/tree/README.md:121-125`).
5. PR 67 is mergeable but its build, lint, and document jobs fail. The
   build job cannot find the passwd shim source and cannot create its
   output directory. Lint reports a redundant boolean comparison in the
   crate CLI. The document job reports two unsafe shell examples and four
   orphan pages. The other three jobs pass. PR 66 has no check result and
   conflicts with main. These are the live GitHub check results for the
   captured heads, not proof that either tree is ready.
   Its main dispatch calls the SSH crate for `remote ssh`; its help
   names `machine ssh` without a matching dispatch arm. The proposed
   task page describes both together, so the next entry separates the
   existing arm from the missing one.
6. The local pg-toolkit README addresses
   portable glibc builds and name resolution. PR 67's proposed SSH client
   is static musl and its server uses a dynamic glibc shim. That makes
   pg-toolkit relevant to a future server packaging choice, but its README
   does not prove this SSH build or its login path.

## Addendum 2026-09-28: relay questions settled

dropssh issue 9 (a client implementer's report dated the same day) and
the live r12 relay documents answer the open relay questions. The relay
forwards node reject reasons to the operator as a text frame plus a
close, publishes the close-code table with sides and actions, and sends
a zero-length keepalive every 25 s. dropssh proved two concurrent
sessions on one socket against the live relay. Pairing and minting are
self-service. A full pair lifecycle ran from this host with zero
residue: pair 200, connect-token status 200, node-token status 403,
stop 200, status after stop 403. Operator decisions: both protocols,
split by use (multiplexed for remote paths, one-pair for local paths
and tests); redacted relay logs may be committed. Open measurement:
node redial pairing, which no document states.
